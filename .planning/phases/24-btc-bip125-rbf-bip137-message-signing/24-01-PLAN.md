<objective>
Add BIP-125 Replace-By-Fee fee bumping to the BTC trust pipeline. The agent can fee-bump a stuck mempool-pending BTC transaction via `prepare_btc_rbf_bump({ txid, newFeeRate })`, and can opt new sends into RBF-signalling via `signalRbf: true` on `prepare_btc_send`.

Purpose: Phase 23 ships BTC sends with RBF disabled (`sequence 0xfffffffe`). A stuck tx cannot currently be bumped. This plan delivers BTC-W-02 — the RBF replacement tool — and the `signalRbf` opt-in flag (Design Fork 1, RESOLVED: adopt Option A) so VaultPilot-prepared sends can themselves be bumped.

Output: New `prepare_btc_rbf_bump` tool; `fetchBtcTx` Esplora helper; `buildBtcPsbt` gains a `sequenceOverride?` parameter; `PreparedTxBtc.kind` widens to `"native" | "rbf"`; five new RBF error codes; `PREPARE_RECEIPT_BTC_RBF_TEMPLATE`; Fixture V hardcoded literal anchor.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent → MCP (`prepare_btc_rbf_bump` args) | `txid` and `newFeeRate` are untrusted — agent could supply a confirmed txid, a non-RBF tx, or an inflated fee claim |
| MCP → Esplora (`GET /tx/{txid}`) | Esplora response is the server's authoritative source for the original tx's input set, sequences, and prevout values |
| MCP → handle store → preview → send | The RBF replacement PSBT must carry an honest per-input BIP-143 sighash binding through the existing drift gate |
| MCP → Ledger device | The device screen is the only trusted display — the RBF replacement's outputs must be visible for user comparison |
