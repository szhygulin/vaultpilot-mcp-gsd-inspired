<objective>
Add BIP-137 message signing to the BTC tooling. The agent can call `sign_message_btc({ wallet, message })` to produce a compact signature proving control of a BTC key — the canonical wallet-ownership-proof shape used for exchange KYC, off-chain attestation, and dApp login.

It is a direct read-then-sign tool that calls the Ledger BTC app's `signMessage` APDU. BIP-322 taproot message signing is explicitly deferred (CONTEXT `<deferred>`).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent → MCP (`sign_message_btc` args) | `wallet` and `message` are untrusted — the agent could supply a transaction-shaped payload disguised as a "message" |
| MCP → Ledger device | The device displays the message text on-screen; it is the only trusted display for what is actually being signed |
| MCP → consumer of the signature | The base64 BIP-137 signature is a wallet-ownership proof — its integrity (correct hash, correct header byte) determines whether downstream verifiers accept it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-24-07 | Elevation of Privilege | BIP-137 signing of an attacker-supplied transaction-shaped payload (a "message" that is actually a serialized tx, tricking the user into authorizing spend-equivalent intent) | mitigate | BIP-137 message signing is structurally NON-spendable: the device prepends the `"Bitcoin Signed Message:\n"` magic prefix and computes double-SHA256 — this preimage CANNOT collide with a Bitcoin transaction sighash (which has no magic prefix and uses a different preimage structure). A signature over a magic-prefixed message is rejected by Bitcoin consensus as a tx signature. The device ALSO displays the literal message text on-screen, so a binary/tx-shaped payload renders as visible garbage the user can reject. Mitigation: (a) magic-prefix is device-applied and cannot be skipped; (b) the LEDGER BLIND-SIGN HASH block surfaces both the hash and the message text for user inspection. Residual: a user who blindly approves a garbage-looking message — accepted residual, consistent with the project's "trust the Ledger screen" model. |
| T-24-08 | Tampering | Double magic prefix producing an invalid / non-standard BIP-137 signature | mitigate | The tool passes ONLY raw message bytes (hex-encoded) to `signBtcMessage`; the Ledger BTC app v2.1+ applies the magic prefix internally (verified in BtcNew.js — RESEARCH §BIP-137 Verified Details). A test asserts the hex passed to the device contains no `"Bitcoin Signed Message:\n"` substring. |
| T-24-09 | Information Disclosure | Message-hash mismatch — the device signs a different hash than the server surfaces | mitigate | The server computes the BIP-137 double-SHA256 hash independently (`computeBip137MessageHash`) and surfaces it in the LEDGER BLIND-SIGN HASH block; Fixture W pins the computation against a known literal; the device computes the same hash from the same preimage — the user can compare. |
| T-24-10 | Tampering | Wrong header byte → signature verifies against the wrong address type or fails | mitigate | `header = v + 39` is fixed for P2WPKH bech32 (BTC-W-03 scope is the segwit address); a unit test pins the header-byte assembly for `v=0` and `v=1`; the 65-byte length is asserted. |
| T-24-11 | Spoofing | Agent supplies a `wallet` address not actually owned / not paired | mitigate | The tool resolves the derivation path ONLY from a matching paired account record (`listAccounts({ chainFilter: "bitcoin" })`); a `wallet` with no matching paired account is refused — the device signs with the paired account's key, not an agent-chosen path. |
| T-24-SC | Tampering | npm/pip/cargo installs | mitigate | RESEARCH §Package Legitimacy Audit confirms NO new packages — `@ledgerhq/hw-app-btc` and `@noble/hashes` are existing Phase 22/23 deps. No install task; no `[ASSUMED]`/`[SUS]` packages. Slopcheck [OK]. |
