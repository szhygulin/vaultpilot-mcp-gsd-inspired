<objective>
Ship `prepare_tron_stake_vote` (TRON-W-06) + `prepare_tron_stake_claim_rewards` (TRON-W-07). Implement the hybrid SR registry loader (D-05) — primary live fetch via `tronWeb.trx.listSuperRepresentatives()`, snapshot fallback `src/tokens/tron-srs.json` on RPC failure, with `srSource` surfacing in CHECKS PERFORMED. Implement the advisory `estimatedRewardSun` field for claim rewards (D-06) — best-effort, demote-to-null on RPC failure, NO intent-vs-reality gate. Pin Fixtures Tron-19-C + Tron-19-D hardcoded literal anchors.

Purpose: TRON voting is the SR-selection mechanism — users delegate their `TRON Power` (= total Stake 2.0 frozen TRX) to elected Super Representatives who run the network. The vote tool's load-bearing concern is the array→map conversion (`votes[]` agent shape → `VoteInfo` map per RESEARCH §Topic 4) — passing the array directly to `tronweb.transactionBuilder.vote()` silently produces malformed calldata (Pitfall 5). The SR registry hybrid policy gives the user verifiable labels without making the system fragile against TronGrid downtime (D-05d — 6h SR rotation cadence; bundled snapshot drift is bounded by release cadence and is advisory, not safety-critical). The claim-rewards tool is the simplest of the 7 — zero-arg, no intent gate, advisory reward estimate.

Output: 2 new protocol files (`tron-vote.ts`, `tron-sr-registry.ts`) + 1 new data file (`tron-srs.json` — ~30 entries) + 2 new tools + 5 new test files + ADDITIVE widening of `handle-store.ts` (`PreparedTxTron.kind` + `TronInstructionSummary` with 2 new kinds each) + ADDITIVE templates in `blocks-tron.ts` + ADDITIVE preview_send TRON branch arms for 2 new stake kinds + ADDITIVE get_tx_verification TRON arm coverage.
</objective>
